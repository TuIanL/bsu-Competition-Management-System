# 02 需求分析（报告章节 · 双端）

> 文档归属：刘腾罡（系统分析员）｜版本：V2｜2026-10-02
> 配套：docs/01_项目范围说明.md、database/schema.sql V1.2、docs/api-contract.md v2（联调草案）
> v2 变更：新增志愿者端（登录/我的班次/报名/签到签退/志愿时长）。

## 1. 项目背景

体育赛事（校运会、院系杯等）依赖大量志愿者承担检票、引导、急救等岗位。当前数据分散、依赖人工沟通，导致：

- 同一志愿者被重复安排到同一班次；
- 志愿者多个班次时间重叠却无人发现；
- 某班次人数已满仍被继续安排；
- 已停用志愿者仍被排班；
- 志愿者无法自助查看自己的班次、无法报名、无法记录实际服务时长；
- 班次名单与缺口只能事后手工统计。

## 2. 项目目标

建立统一的 **体育赛事志愿者调度系统（双端小程序）**：

1. 管理端统一维护志愿者、赛事、岗位、班次基础数据；
2. 以 `assignment` 记录调度（志愿者 ↔ 班次多对多），以 `application` 记录志愿者报名意向；
3. 数据库约束（UNIQUE/CHECK/FK）+ 后端业务层校验双重保证完整性；
4. 志愿者端支持自助查看班次、报名、签到签退、查看实际志愿时长；
5. 展示班次名单与缺口统计，支撑现场调度决策。

## 4. 核心业务规则

### 4.1 调度四规则（管理员分配时触发）

| 规则 | 描述 | 控制层 | 失败 message |
|---|---|---|---|
| **R1 状态** | 仅 `ACTIVE` 志愿者可被调度 | 业务层 | 该志愿者已停用，无法安排 |
| **R2 重复** | 同一 `volunteer_id+shift_id` 不可重复 | DB `UNIQUE(shift_id,volunteer_id)` + 业务层先查 | 该志愿者已在本班次 |
| **R3 时间冲突** | 志愿者未取消的班次时间不得重叠（`ASSIGNED`/`COMPLETED`；边界 `end==start` 允许） | **业务层**（`core_queries.sql` ⑥ 跨行区间比较） | 该志愿者在该时段已有其他班次 |
| **R4 满员** | 已安排人数达 `required_count` 后不可再安排 | **业务层**（聚合计数） | 该班次已满员 |

### 4.2 志愿者端规则（v2 新增）

| 规则 | 描述 | 控制层 | 失败 message |
|---|---|---|---|
| **R5 报名唯一** | 同一志愿者不可重复报名同一班次 | DB `UNIQUE(volunteer_id,shift_id)` | 该岗位已经报名 |
| **R6 越权保护** | 志愿者只能签到/签退/查看自己的 assignment | 业务层（session 校验） | 无权操作该数据（403） |
| **R7 签到时序** | 必须先签到才能签退；签退时间不得早于签到时间 | 业务层 + DB CHECK(check_out_at >= check_in_at) | 请先签到 |
| **R8 时长口径** | 志愿时长 = Σ(check_out_at − check_in_at)，仅统计 `COMPLETED` | 业务层聚合 | — |

> 设计要点：R2/R5/R7 的关键完整性条件有数据库约束兜底；R1/R3/R4/R6/R8 需业务层检查或聚合。这体现"数据库约束 + 业务逻辑两层协同"，是答辩重点。

## 5. 非功能需求

- **界面清晰**：页面字段与 api-contract 一致。
- **错误信息可理解**：所有失败返回中文 message，不暴露 traceback（P0-15）。
- **样例数据可重置**：seed 生成 ≥20 名志愿者、3 场赛事和班次数据；至少包含未来可报名班次与已满员班次，覆盖报名和满员提示。
- **演示稳定**：开发者工具演示双端主流程，准备体验版二维码/截图/录屏兜底。
